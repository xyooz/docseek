# DocSeek Windows Beta 验证指南

这份指南用于把 DocSeek 从“CI 中可用”推进到“真实 Windows 办公环境可长期使用”。Beta 阶段优先验证稳定性、检索有效性、资源占用和数据边界，不追求继续增加功能。

每次测试建议复制 [`BETA_RESULT_TEMPLATE.md`](BETA_RESULT_TEMPLATE.md) 作为本轮记录。测试结论必须能追溯到具体版本、机器、语料规模和测试步骤，而不是只记录“感觉正常”。

## 1. 测试原则

- 先使用明确允许测试的目录，不要为了压力测试主动扩大涉敏数据范围。
- DocSeek 只应读取用户主动添加的索引目录；测试过程中不得通过管理员权限绕过原文件 ACL。
- 不为测试故意复制真实敏感正文到公开仓库、Issue、聊天记录或截图中。
- 记录事实，不把单台机器或单批语料结果外推成正式 SLA。
- 出现异常时优先保留可复现步骤和脱敏诊断，不复制文档正文到 Issue/聊天记录。
- 每轮只改变少量变量。例如本地 SSD 与网络盘、Office 与 WPS 应分开记录，避免混成一个无法解释的结果。

## 2. 测试分级

不要一开始就把整个办公目录交给 Beta 版本。建议按三个阶段推进。

### A. Smoke：1k～5k 文件

目标：先发现格式兼容、安装、基本索引和明显崩溃问题。

至少完成：

- Setup 和 Portable 各启动一次；
- 首次完整索引；
- 10 条已知目标查询；
- 创建 / 修改 / 重命名 / 删除各一次；
- 一次睡眠 / 唤醒；
- 检查索引问题列表和脱敏诊断。

只有 A 阶段没有阻断问题，才扩大语料。

### B. Scale：10k～50k 文件

目标：验证主要办公规模下的首次索引、增量维护和搜索体验。

至少记录：

- 首次索引耗时；
- 文件格式分布；
- 索引数据库大小；
- 索引成功 / 问题数量；
- CPU 和内存峰值；
- 大 Excel / PDF / 旧格式的长尾现象；
- 20 条以上真实查询的 Top1 / Top5 / Top10；
- 第二次无变化完整校准耗时。

### C. Soak：4～8 小时，随后 1～3 天日常使用

目标：验证长期常驻、睡眠唤醒、Watcher 自愈和资源稳定性。

期间正常进行文件保存、移动、重命名和搜索，不需要人为制造极端压力。实际需要同步盘或网络盘时，再单独增加对应场景。

## 3. 建议测试环境

至少覆盖两类机器：

1. 普通办公本：8～16 核 CPU、16 GB 内存、SSD；
2. 较低配置办公本：4～8 核 CPU、8 GB 内存、SSD。

每轮至少记录：

- Windows 10 / 11 及版本；
- CPU 型号或核心 / 线程数量；
- 内存容量；
- SSD / HDD；
- DocSeek 版本或 commit；
- Setup / Portable；
- 是否安装 WPS / Microsoft Office；
- 是否涉及网络盘 / OneDrive / 企业同步盘。

如果实际场景涉及网络盘、OneDrive/企业同步盘、WPS 或旧版 Office，再分别增加对应样本，不要把它们和本地 SSD 结果混在一个指标里。

## 4. 安装与卸载

优先使用 `DocSeek-<version>-Setup-x64.exe`：

- 使用普通 Windows 用户安装，确认不出现 UAC 管理员提权要求；
- 默认安装路径应位于 `%LOCALAPPDATA%\Programs\DocSeek`；
- 确认开始菜单入口可启动；
- 可选桌面快捷方式正常；
- 安装后不需要单独安装 Python；
- 内网无互联网环境下能够安装和首次启动；
- 卸载后程序目录应被删除；
- `%USERPROFILE%\.docseek` 中的索引/设置默认保留，除非用户主动清理。

Portable ZIP 另做一次“解压到新目录 → 直接启动”的验证。

**阻断条件：**需要管理员权限才能正常使用、无 Python 环境无法启动、卸载误删源文件或用户未确认的数据。

## 5. 首次索引

### 5.1 开始前

- 确认测试目录范围正确；
- 记录文件总量和主要格式数量；
- 如果本机已有 DocSeek 索引，说明是“全新索引”还是“已有索引升级”；
- 不要为了得到更好数据而关闭杀毒、EDR 或正常办公安全策略；
- 测试目录中准备少量已知目标文件，用于之后确认搜索和更新结果。

### 5.2 首次索引记录

记录：

| 指标 | 记录内容 |
| --- | --- |
| 文件总量 | 仅数量 |
| 格式分布 | `.docx/.xlsx/.pdf/.wps/...` 数量或比例 |
| 开始 / 结束时间 | 用于计算墙钟耗时 |
| 已索引文件数 | 从索引概况读取 |
| 索引问题数 | 按错误类型汇总，不外发文件名 |
| 数据库占用 | `docseek.db` 及必要 sidecar 总量 |
| CPU 峰值 | 任务管理器观察值即可 |
| 内存峰值 | 任务管理器观察值即可 |
| UI 响应 | 正常 / 短暂卡顿 / 明显不可用 |
| 长尾文件 | 是否出现单个文件长时间占用解析 |

索引设置中的“索引概况”可直接读取文件数、空间占用、目录状态、问题数和最近完整校准时间。

### 5.3 第二次完整校准

首次索引完成且文件未变化时，再执行一次完整校准。记录耗时和结果：

- 不应重新解析绝大多数未变化文件；
- 已索引文件数不应无原因变化；
- 问题文件在退避期内不应被无休止重复解析；
- 数据库不应因为无变化扫描持续异常膨胀。

## 6. 检索质量

不要只测试“肯定能搜到”的合成词。每位测试者准备至少 20 个自己真实会搜索的问题，并事先知道目标文件。

建议覆盖：

- 只记得正文中的业务术语，不记得文件名；
- 记得文件名的一部分；
- 记得 Excel 工作表名；
- 记得 PPT 某页标题；
- 记得 Word 标题 / 章节；
- 同一个概念在目标文件多个章节出现；
- 一个很长的 PDF 里大量重复同一词，但并不是最佳目标；
- 需要组合 `ext:` / `path:` / 时间 / 大小筛选；
- 中文、英文、数字混合关键词。

对每条查询记录：

| 字段 | 说明 |
| --- | --- |
| 查询编号 | Q01、Q02……，便于复现 |
| 查询 | 外发记录时可写成脱敏类别 |
| 目标文件是否出现 | 是 / 否 |
| 排名 | Top1 / Top5 / Top10 / >10 / 未找到 |
| 首屏体感 | 即时 / 可接受 / 明显慢 |
| 是否需要改写查询 | 是 / 否 |
| 最佳结果是否合理 | 是 / 否 |
| 备注 | 排名异常、筛选异常、结果解释问题 |

一轮测试结束后至少计算：

- **Top1 命中率** = 已知目标排第 1 的查询数 / 查询总数；
- **Top5 命中率** = 已知目标进入前 5 的查询数 / 查询总数；
- **Top10 命中率**；
- **改写率** = 为找到目标而必须修改查询的比例。

Beta 阶段最重要的是记录这些数值如何随版本变化，而不是把小样本结果宣传成“真实准确率 100%”。CI curated corpus 只是防退化门槛，不能替代真实查询集。

## 7. 增量更新与 Watcher 最终一致性

在一个专门的测试目录内依次验证：

| 操作 | 预期结果 |
| --- | --- |
| 新建受支持文件 | 新内容最终可搜到 |
| 修改正文 | 新内容可搜到，旧内容不再残留 |
| 重命名 | 新路径存在，旧路径不再出现 |
| 删除 | 搜索结果最终消失 |
| 移动到子目录 | 仅保留新路径 |
| 子目录整体移动 | 最终与磁盘目录一致 |
| Office/WPS 覆盖保存 | 临时文件不成为长期索引结果 |
| 加入排除规则 | 已有对应索引在校准后被移除 |
| 取消排除规则 | 文件可重新进入索引 |
| 睡眠 / 唤醒后修改 | 唤醒后能够自动收敛 |
| 批量复制文件 | 不因持续事件而永久不 flush |

不要只检查“watcher 收到事件”，最终判定标准是：**稳定一段时间后，磁盘上应该存在的文件、DocSeek 索引和搜索结果三者一致。**

开发环境还可运行已有 soak harness：

```powershell
python benchmarks/watcher_soak.py --cycles 500 --interval 0.2
```

需要拉长墙钟时间时可提高 `--interval`；脚本只会在自己的 `docseek-soak-*` 测试目录中生成和修改文件。

## 8. 睡眠 / 唤醒专项

至少执行一次：

1. DocSeek 正常运行且 watcher 已启动；
2. 记下当前已知测试文件的搜索状态；
3. Windows 进入睡眠；
4. 唤醒后立即修改 / 新建一个测试文件；
5. 等待 watcher health check / reconciliation 工作；
6. 搜索确认新状态；
7. 查看最近完整校准时间是否合理更新；
8. 确认没有重复结果和旧路径。

如果实际存在同步盘，可再做“睡眠期间由其他设备改变同步内容”的独立案例。

## 9. 长时间运行

建议至少做：

- 4～8 小时连续常驻；
- 1～3 天包含睡眠 / 唤醒的日常使用；
- 同步盘 / 网络盘断开并恢复（如实际使用会涉及）。

建议在开始、1 小时、4 小时、结束时各记录一次：

- DocSeek 内存；
- 空闲 CPU；
- `docseek.db` + `-wal` + `-shm` 大小；
- 索引问题数；
- watcher 是否仍能感知测试文件变化。

关注：

- 内存是否持续单向增长且无法回落；
- CPU 空闲时是否仍持续高占用；
- watcher 是否停止响应；
- SQLite/WAL 是否持续异常膨胀；
- 搜索会话是否在多次索引后仍正常；
- 关闭应用是否干净退出。

不要仅凭一次高峰判定“内存泄漏”。重点看多次采样是否持续单向增长，并结合操作负载判断。

## 10. 异常文件与恢复

至少覆盖：

- 被其他程序锁定的文件；
- 无权限文件 / 目录；
- 损坏 Office / PDF；
- 超过当前大小上限的文件；
- 0 KB / 空文件；
- 密码保护或无法读取的文档；
- 旧 `.doc/.xls/.ppt`；
- `.wps/.et/.dps` 等实际 WPS 样本。

对失败文件至少验证：

1. 整体索引任务仍能继续；
2. 问题能够在索引问题列表中看到；
3. 同一未变化坏文件不会在短时间内无限重试；
4. 人工重试能够绕过普通全量扫描退避；
5. 文件被修复 / 替换后能够重新索引；
6. 解析器版本升级后仍有重新尝试的路径。

目标不是所有文件都强行解析成功，而是失败能够被记录、解释、重试，并且不能让整个索引任务卡死。

## 11. 维护与恢复

至少在测试数据上验证一次：

- 创建索引备份；
- 一键重建索引，确认索引目录 / 用户偏好按设计保留；
- 一键清理或重置时，确认界面明确说明不会删除源文件；
- 从有效备份恢复；
- 选择无效 SQLite / 损坏备份时应拒绝恢复；
- 恢复前生成安全备份，出现问题可以回退。

任何维护操作都不得写入、移动或删除用户源文档。

## 12. 脱敏诊断

出现问题时，在“索引设置 → 索引概况”使用“导出脱敏诊断…”。

诊断 JSON 只应包含：

- DocSeek 版本与 schema 版本；
- Windows / Python / SQLite 运行环境；
- 已索引文件数量和数据库占用；
- 活动 / 暂停目录数量；
- 索引问题按错误代码的数量；
- 排除目录 / 文件规则数量；
- 最近完整校准时间；
- 文件大小上限等非内容配置。

明确不包含：

- 索引目录路径；
- 文件路径 / 文件名；
- 文档正文；
- 索引问题详情文本；
- 搜索历史或收藏查询。

即使是脱敏诊断，提交到外部平台前仍建议按所在单位的数据处理规范检查。

## 13. 缺陷分级

### Blocker — 必须停止扩大 Beta

出现任一项都不应继续扩大测试范围：

- DocSeek 修改、移动或删除源文件；
- 索引数据库损坏且无可恢复路径；
- 正常目录中单个异常文件可持续卡死整个索引；
- 应用出现稳定可复现的启动崩溃 / 崩溃循环；
- 删除 / 重命名后的旧敏感内容长期无法从索引移除；
- 明显绕过用户原有 ACL 或索引了未配置范围。

### Major — 修复后再进入更大规模

例如：

- watcher 在常见保存 / rename 场景长期失去一致性；
- 睡眠 / 唤醒后无法自行恢复；
- 10k～50k 规模下普通搜索明显不可用；
- 某常见办公格式大面积失败；
- 内存或 WAL 在普通使用中持续无界增长；
- 维护 / 恢复功能无法按设计工作。

### Minor — 可记录后继续 Beta

例如：

- 个别格式或损坏文件无法解析但已被隔离；
- 排名存在可优化案例但目标仍能进入合理 TopK；
- UI 文案、布局或非关键交互问题。

## 14. Beta 退出条件

进入更大范围试用前，建议至少满足：

- Setup / Portable 在目标办公机可正常启动；
- 无源文件误删、误改；
- A、B、C 三阶段均没有未解决 Blocker；
- 典型增删改移后索引最终一致；
- 常用真实查询的 Top5 表现达到团队可接受水平，并已有可比较的基线记录；
- 10k～50k 规模下交互搜索仍保持可接受响应；
- 连续运行和睡眠 / 唤醒后 watcher 可恢复；
- 失败文件不会拖垮整个索引；
- 已知问题均有可理解的提示或恢复路径；
- 备份 / 重建 / 恢复路径经过真实验证；
- 诊断能力足以支持不暴露办公路径 / 正文的故障定位。

代码签名、企业软件分发、索引 ACL / 加密和正式运维策略仍属于更大范围部署前的独立门槛。
